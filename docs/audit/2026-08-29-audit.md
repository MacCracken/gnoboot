# gnoboot 0.6.2 — pre-1.0 security / hardening audit

**Date:** 2026-08-29 · **Scope:** the whole boot path — `src/main.cyr` (740
lines) at tag `0.6.2` (`741e935`), plus `SECURITY.md`'s published threat model ·
**Method:** re-derive from source — every claim below was verified by reading the
implementation, not its comments (the audit-re-derive discipline). Two language
semantics that findings depend on (`%` on a negative dividend, `0 - i64::MIN`)
were verified **empirically** against the pinned toolchain rather than assumed;
see § Language semantics verified.

**This pass changed no code.** It is the scoping document for **v0.7.0**, which
merges roadmap **M5** (multi-`PT_LOAD`) and **M7** (boot-info validation hooks)
— because the audit found they are the same twenty lines. Gates at time of
audit: build clean, `verify_pe.sh` PASS, `ovmf_smoke.sh` PASS
(`gnoboot v0.6.2: handing off to kernel`).

## Posture decision

gnoboot is a **UEFI Application in boot-services context** — full firmware
privilege, no MMU isolation, and after `ExitBootServices` there is no console to
report anything on. That inverts the usual cost/benefit of hardening checks:

- **There is no hot path.** Every check named here runs once, pre-EBS, on a
  path already dominated by firmware file I/O. The tentib/tarka "cold paths
  only" rule costs nothing to satisfy here because *every* path is cold.
- **The only two outcomes that matter** are "boot correctly" and "fail to a
  4-char code on ConOut *before* EBS." Anything that reaches EBS in a bad state
  produces a silent triple-fault with no diagnostic — the worst outcome the
  project has, and the reason `CLAUDE.md` says *correctness over cleverness*.

So gnoboot follows the **fail-loud-before-EBS** posture: every value that comes
from outside gnoboot's own binary — the ESP file, or firmware — is validated
before it can influence an allocation, a copy length, or a jump target. The
existing `efi_fail(st, &code_XX)` mechanism already provides the reporting
channel; the finding bar is *anything that reaches ExitBootServices, or a
firmware allocation, on an unvalidated externally-supplied value*.

## The headline: SECURITY.md documents defenses that are not implemented

`SECURITY.md` § Threat model states gnoboot defends against:

> **Malformed kernel files** — `\boot\agnos` with bad ELF headers, oversized
> program-header counts, malformed PT_LOAD entries. Bounds-checked at parse
> time; fail to a status print before EBS.

**None of the three clauses holds as written.** The program-header *count* is
never read (F2), no `PT_LOAD` field is bounds-checked (F3, F4), and the ELF
header check is one byte (F1). The other two clauses in that section —
fail-closed `GetMemoryMap` and the straight-line map-key path — **do** hold and
were verified (S2, S1).

This is the single most important result of the pass. A published threat model
that overstates coverage is worse than one that admits the gap, because it stops
the next reader from looking. **`SECURITY.md` must be corrected in the same cut
that lands the fixes** — either the prose comes down to match the code, or
(preferred, and the v0.7.0 plan) the code comes up to match the prose.

## Threat-model note — what this does and does not change

`SECURITY.md` is explicit that gnoboot does **not** defend against a *modified*
kernel binary: with no signature verification, anyone who can write
`\boot\agnos` can simply supply a valid kernel. That correctly caps the severity
of everything below — **these are not privilege escalation**, because the
attacker who could trigger them already has the outcome by an easier route.

What they are is a **fail-closed violation on the non-adversarial trigger**, and
that trigger is routine: a truncated `\boot\agnos` from an interrupted `dd`, a
bad USB write, a failed ISO build, a partially-flushed `mcopy`. Today those
produce *jump into partially-initialized memory, triple-fault, no console*.
The threat model promises *fail to a status print before EBS*. Severities below
are assigned against that boundary, per `SECURITY.md`'s rubric.

## Findings

| # | sev | finding | class | disposition |
|---|-----|---------|-------|-------------|
| **F1** | HIGH | **Pre-load ELF validation is one byte.** [`main.cyr:409`](../../src/main.cyr#L409) checks only `load8(&elf_hdr+0) != 0x7F`. No `ELF` magic bytes 1–3, no `EI_CLASS` (64-bit), no `EI_DATA`, no `e_machine` (0x3E), no `e_phentsize`. Any file whose first byte is `0x7F` proceeds to `e_phoff = load64(&elf_hdr+0x20)` — a garbage 64-bit offset that drives `SetPosition`, then a garbage `phdr`, then `AllocatePages` and a `Read` at an address the file chose. The 4-byte re-check at [`:499`](../../src/main.cyr#L499) is a **backstop, not a gate**: it fires only after the allocation and the copy have already happened. | unvalidated trust boundary | → **v0.7.0** (this is M7's "ELF magic + machine match", but the check belongs *before* `e_phoff` is used, not only after the load) |
| **F2** | MEDIUM | **`e_phnum` is never read; only program header [0] is honored.** [`main.cyr:411–424`](../../src/main.cyr#L411) seeks to `e_phoff`, reads exactly one 56-byte `Elf64_Phdr`, and hard-fails if it is not `PT_LOAD`. Two consequences: (a) a kernel linked with `PT_PHDR` or `PT_INTERP` first — the normal output of many link configurations — fails with `PT` even though it is valid; (b) a kernel with 2+ `PT_LOAD` segments (any hardened RX-text / RW-data split) **silently loads only the first** and jumps into a partially-loaded image. `e_phentsize` is likewise assumed to be 56 with no check. Works today only because agnos happens to link as a single `PT_LOAD`. | silent under-load / forward-compat | → **v0.7.0** (this *is* roadmap M5) |
| **F3** | HIGH | **The kernel segment `Read` has no short-read check.** [`main.cyr:475–477`](../../src/main.cyr#L475) sets `read_sz = p_filesz`, calls `Read`, and never compares `read_sz` back. UEFI 2.10 §13.5.1: `Read` rewrites `BufferSize` to bytes *actually* transferred and still returns `EFI_SUCCESS`. A truncated `\boot\agnos` therefore loads short, succeeds, and the BSS zero-fill at [`:507`](../../src/main.cyr#L507) covers only `[p_filesz, p_memsz)` — so the un-read tail `[actual, p_filesz)` keeps whatever `AllocatePages` returned, which UEFI 2.x §7.2 declares **undefined**. gnoboot then jumps into it. The same gap applies to the two header reads at [`:406`](../../src/main.cyr#L406) and [`:416`](../../src/main.cyr#L416). **`load_esp_blob` already guards exactly this** at [`:345`](../../src/main.cyr#L345) — *the optional path is stricter than the mandatory one.* | bypasses an explicit boundary | → **v0.7.0** |
| **F4** | HIGH | **`p_filesz` / `p_memsz` / `p_offset` are used unbounded.** Two distinct hazards from the same omission: **(a)** `p_filesz > p_memsz` is never rejected — `pages` is computed from `p_memsz` at [`:440`](../../src/main.cyr#L440), then `p_filesz` bytes are read into that allocation at [`:476`](../../src/main.cyr#L476) → a copy overrun of attacker-chosen length past the end of the allocation. **(b)** `(p_memsz + 0xFFF) / 0x1000` wraps: with `p_memsz` in `[0xFFFFFFFFFFFFF001, 0xFFFFFFFFFFFFFFFF]` (i.e. `-4095..-1` as i64) the sum is `0..4094` and truncated division yields **`pages = 0`** — a zero-page allocation followed by a real `Read`. Neither is bounded against the file's actual size, which is never queried. **`load_esp_blob` caps at 1 GiB** at [`:331–334`](../../src/main.cyr#L331) *with a comment naming this exact overflow* — the mandatory path never got the same treatment. | copy overrun / integer wrap | → **v0.7.0** |
| **F5** | MEDIUM | **The handoff struct has no END terminator, and its own layout comment says it does.** [`main.cyr:490`](../../src/main.cyr#L490) stores the KASLR `kernel_base` at `boot_info + 0x70` — the slot the layout block at [`:192`](../../src/main.cyr#L192) still documents as `tag[] type=0 END terminator`. Since v0.6.0 a consumer walking the tag stream reads `type = low32(kernel_base)` (e.g. `0x02000000`) and `size = high32(kernel_base)` (0), then either spins on a zero-size advance or runs past the 120-byte struct. `struct_size` still reports 120. **Not live-exploitable** — agnos reads fixed offsets and no shipped consumer walks tags — but the v1.0 criterion is *"handoff struct v1 finalized … every reserved tag-type slot listed,"* and the struct as shipped contradicts its own specification. | contract / doc divergence | → **M4** must resolve: declare it a flat 120-byte struct and drop the tag-stream concept, **or** grow to 128 and restore END at 0x78. Layout comment corrected in **v0.7.0** either way. |
| **F6** | MEDIUM | **RDRAND failure silently voids KASLR.** `rdrand_u64` ([`:219–227`](../../src/main.cyr#L219)) never checks CF. On failure `rcx` is architecturally 0, so the slide picks slot 0 = 32 MB — and because all 16 re-roll attempts at [`:447–456`](../../src/main.cyr#L447) call the same failing instruction, they all pick the *same* address; the first `AllocatePages` succeeds and the loop exits. The result is a **fixed, predictable kernel base that is indistinguishable at the kernel from a randomized one** — `boot_info+0x70` reports 32 MB, which is a legal slide value. The comment at [`:215`](../../src/main.cyr#L215) acknowledges the fallback but treats it as benign; it is benign for *booting* and total for *the security property*. | security property fails open, silently | → **v0.7.0**: retry `rdrand` on CF=0 (Intel guidance: 10 attempts), and set a `flags` bit so the kernel can report *"KASLR: entropy unavailable"* rather than a base that merely looks random. |
| **F7** | LOW | **`0 - i64::MIN` escapes the KASLR window.** [`main.cyr:451`](../../src/main.cyr#L451) normalizes with `if (ksl_r < 0) { ksl_r = 0 - ksl_r; }`. Verified empirically (§ Language semantics): negating `i64::MIN` leaves it negative, and `%` is C-truncated, so `ksl_r % 111` is **negative** and `p_paddr` lands below the intended 32 MB floor. Self-healing in practice — `AllocatePages(AllocateAddress)` refuses, the re-roll fires, and the `0x100000` fallback catches the rest — and the probability is 2⁻⁶⁴. | integer edge | → **v0.7.0**, one token: mask instead of negate (`ksl_r & 0x7FFFFFFFFFFFFFFF`). |
| **F8** | LOW | **The memory map cannot grow.** [`:682`](../../src/main.cyr#L682) and [`:703`](../../src/main.cyr#L703) pass a fixed 16384 into `mm_buf[2048]` (= 16384 bytes exactly — the size is **honest**, so there is no overrun; S2). But a machine whose map exceeds 16 KB (≈340 descriptors at 48 B) gets `EFI_BUFFER_TOO_SMALL` and simply does not boot, reporting only `MM`. UEFI's own idiom is the two-call pattern. Note the fix has an ordering constraint: the sizing `AllocatePages` must happen **before** the final `GetMemoryMap`, or it invalidates the map key. | availability / brittleness | → **v0.7.0** if cheap, else M7. Not a correctness bug. |
| **F9** | LOW | **Firmware-supplied counts are inconsistently bounded.** The ACPI config-table walk **caps** `nents` at 256 ([`:669`](../../src/main.cyr#L669), with a comment saying why), but the GOP `QueryMode` loop at [`:572`](../../src/main.cyr#L572) iterates to a raw `max_mode` — and `load32` **zero-extends** (verified empirically), so a firmware reporting `MaxMode = 0xFFFFFFFF` spins ~4×10⁹ `QueryMode` calls pre-EBS. Also unchecked: `ctab == 0` with `nents > 0` dereferences near address 0 ([`:673`](../../src/main.cyr#L673)), and `dsz == 0` divides by zero at [`:710`](../../src/main.cyr#L710). All require malformed firmware, which is outside the threat model — but the *inconsistency* is the finding: one walk is bounded and the other two are not. | defense-in-depth | → **v0.7.0**, three one-liners. |
| **F10** | INFO | `q_w * q_h` at [`:585`](../../src/main.cyr#L585) multiplies two zero-extended u32s into i64; adversarial values overflow to negative, which fails the `q_px > best_px` test and skips the mode. Fail-safe by construction, as the block's own comment claims. No action. | — | none |

## Verified sound (no change)

| # | path | verdict |
|---|------|---------|
| **S1** | **No boot service is called between `GetMemoryMap` and `ExitBootServices`.** The hard rule from `CLAUDE.md`. Verified line by line: [`:703`](../../src/main.cyr#L703) refreshes the map, [`:710–711`](../../src/main.cyr#L710) do pure arithmetic and stores into `boot_info` (no firmware call), [`:715`](../../src/main.cyr#L715) calls EBS. `efi_clear` / `efi_print` are both *before* the refresh, and the code comment correctly explains why the refresh exists. | **SOUND** |
| **S2** | **`GetMemoryMap` fails closed.** `mm_buf[2048]` is 2048 × 8 = **16384 bytes**, and the size passed in is exactly 16384 — the buffer is not over-declared, so `EFI_BUFFER_TOO_SMALL` is returned and honored rather than the map being truncated into a short buffer. Matches the `SECURITY.md` claim exactly. (Brittleness is F8; safety is sound.) | **SOUND** |
| **S3** | **No path-traversal surface.** All three ESP paths are compile-time UTF-16LE constants — `\boot\agnos` [`:71`](../../src/main.cyr#L71), `\boot\initramfs` [`:87`](../../src/main.cyr#L87), `\boot\cmdline` [`:99`](../../src/main.cyr#L99). Nothing is concatenated, and no external input reaches a path argument. The roadmap's *"no path traversal in `\boot\agnos` resolution"* criterion is **met by construction**. | **SOUND** |
| **S4** | **The optional-fill path (`load_esp_blob`) is correctly hardened.** `GetInfo`-derived size, a 1 GiB sanity cap against the page-count overflow, a short-read check, and benign-`0` on every failure — it never calls `efi_fail`. This is the model the mandatory kernel path should be brought up to; F3 and F4 are literally *"do what this function already does."* | **SOUND** |
| **S5** | **Header read buffers are exactly sized.** `elf_hdr[8]` = 64 bytes for a 64-byte read; `phdr[7]` = 56 bytes for a 56-byte read. No overflow on either. (Short *reads* are F3; over-reads do not exist.) | **SOUND** |
| **S6** | **BSS is zeroed, and for the documented reason.** [`:503–511`](../../src/main.cyr#L503) zeroes `[p_filesz, p_memsz)` because `AllocatePages` does not guarantee zeroed memory (UEFI 2.x §7.2). The roadmap's M5 text still lists "zero-fills BSS" as future work — **the roadmap is stale here; the code already does it.** | **SOUND** (roadmap text needs correcting) |
| **S7** | **A failed `ExitBootServices` reports rather than proceeding.** [`:717–723`](../../src/main.cyr#L717) calls `efi_fail` and returns to firmware, which is correct — a failed EBS means boot services are still alive, so the console is still valid. | **SOUND** |
| **S8** | **The handoff register sequence is intact.** `mov rdi, rax` then a stack-local `mov rax,[rbp-N]` then `jmp rax` — nothing between the two touches RDI. Re-verified by disassembly at the v0.6.2 cut under 6.5.35 and unchanged here. | **SOUND** |
| **S9** | **Optional fills are genuinely benign.** initramfs / cmdline / RSDP each leave their `boot_info` field at 0 on any failure and never abort the boot. A normal `.img` boot with no extra ESP files is unaffected. | **SOUND** |

## Language semantics verified

Two findings depend on cyrius integer semantics, which were **measured against
the pinned toolchain** rather than assumed (compiled and run; exit-code probes
retained in the session scratchpad):

| probe | result | used by |
|---|---|---|
| `(0 - 7) % 111` | **negative** — `%` is C-truncated, not floored | F7 |
| `0 - i64::MIN` | **stays negative** — two's-complement identity, no trap | F7 |
| `load32` of `0xFFFFFFFF` | **zero-extends** to 4294967295, does not sign-extend | F9, F10 |

## Out of scope / accepted contract

- **Kernel signature verification** — explicitly deferred to post-v1 Secure Boot
  / TPM work by `SECURITY.md`. Nothing here changes that; F1–F4 are about
  *malformed* input, not *malicious* input.
- **Firmware compromise** — gnoboot trusts Boot Services return values by
  design. F9's bounds are defense-in-depth against firmware *bugs*, not against
  a hostile firmware, which is unwinnable at this layer.
- **`src/test.cyr` does not build** — pre-existing, documented in `state.md`,
  touches no release gate. Unchanged by this pass and still unresolved.

## Reconciliation with the roadmap

The audit did not produce a work list parallel to the roadmap — it produced
**the same list, better ordered**:

- **M5 (multi-`PT_LOAD`)** is F2. It is not only a forward-compat feature; it is
  a silent-under-load bug today.
- **M7 (validation hooks)** is F1 + F4 + the `struct_size` self-consistency
  check. Its "memmap sanity" hook overlaps F8.
- **M4 (handoff spec doc)** must resolve F5 before it can be written — the spec
  cannot document a tag stream that no longer has a terminator.
- **M6 (verbose *serial* diagnostics)** is worth re-scoping before it is built:
  archaemenid has no serial cable, which is why the 0.4.0 audit results sink to
  CMOS. A serial-only diagnostic mode does not help the one box that matters.

**Recommended v0.7.0 scope** — *"ELF-load hardening"*, one release, one code
region: F1, F2, F3, F4, F6, F7, F9, plus F5's comment correction, plus the
`SECURITY.md` reconciliation. F8 folds in if the allocate-before-final-map
ordering proves clean; otherwise it defers to M7.
